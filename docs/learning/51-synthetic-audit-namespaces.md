# Lesson 51: Synthetic audit namespaces

## Established concept

Every audit-created record needs a unique owner and run marker.

## Plain-language explanation

Make test data recognisable without pretending it belongs to a learner.

## Why AI agents struggle

Convenient normal accounts and generic titles blur ownership and cleanup boundaries.

## Itzako example

Phase 2H requires a pre-existing synthetic subject plus one `KAG-2H-*` marker.

## Guard implementation

The plan refuses dispatch when synthetic ownership, token scope, or namespace isolation is unproven.

## Trade-offs

Synthetic identities need advance operational setup, but they protect real learner data.

## Failure modes

Normal cookies, unsupported metadata fields, marker reuse, or unverified test-account claims.

## Practical exercise

Design marker placement across source URL, title, idempotency key, and operation metadata.

## Transfer to another project

Use synthetic identities for CRM imports, billing tests, and support automation.

## Key takeaway

Synthetic data is safe only when ownership is independently provable.
