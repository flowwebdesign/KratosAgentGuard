# Lesson 59: Environment equivalence versus production equivalence

## Established concept

Matching source and contracts does not make two runtime environments equivalent in every operational respect.

## Plain-language explanation

You can prove the same backend build, migration, and request contract while leaving production deployment, provider, and browser state untested.

## Why AI agents struggle

Passing integration tests encourage a broad readiness claim that the evidence does not support.

## Itzako example

Phase 2I proves the sealed extension, isolated backend, queue, and PostgreSQL path; canonical runtime, real provider, and normal Chrome remain unproven.

## Guard implementation

The final verdict is qualified and carries `CANONICAL_RUNTIME_GOLDEN_JOURNEYS_NOT_EXECUTED` as the first remaining blocker.

## Trade-offs

Qualified verdicts are less concise but prevent accidental promotion.

## Failure modes

Calling an audit runtime production, treating a fake provider as real-provider proof, or transferring a fresh-profile result to normal Chrome.

## Practical exercise

For one passing test, enumerate source, build, runtime, database, identity, provider, and browser scopes separately.

## Transfer to another project

Use scope-qualified verdicts for staging releases, hardware labs, and sandbox APIs.

## Key takeaway

Equivalence is always about named boundaries; untested boundaries stay unproven.
